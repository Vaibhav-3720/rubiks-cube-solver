# Rubik's Cube Solver

A 3x3 Rubik's Cube solver in modern C++17. It represents the cube as a
compact bitboard, finds solutions with IDA* guided by a precomputed
corner pattern database, and includes a simpler 3D-array cube model used
purely as a correctness reference for testing.

## What's here

```
include/
  Model/            Cube representations (interface + two implementations)
  Solver/           Search algorithms (BFS, DFS, IDDFS, IDA*)
  PatternDatabases/  Corner pattern database + supporting math
src/                 Matching .cpp files for everything above
tools/
  generate_corner_db.cpp   Standalone tool to (re)build the pattern database
data/
  cornerPatternDB.bin      Prebuilt corner pattern database (~44 MB)
```

### Cube models

- **`RubiksCubeBitboard`** — the cube used everywhere for real solving.
  Each face is packed into a single `uint64_t` (8 bytes, one per
  non-center sticker), and moves are pure bit-shifts/masks. This is what
  makes the solver fast.
- **`RubiksCube3dArray`** — a plain `char[6][3][3]` cube. It's slower but
  much easier to reason about, and is used as a trusted reference to
  cross-validate the bitboard model's move logic (see [Testing](#testing)).

Both implement the same abstract `RubiksCube` interface, so solvers are
written generically against it.

### Solver

The real solver is `IDAstarSolver` (`include/Solver/IDAStar.h`): iterative-
deepening A* using the corner pattern database as an admissible-ish
heuristic (see [Pattern database depth](#pattern-database-depth) for the
"-ish"). `BFS`, `DFS`, and `IDDFS` also exist as simpler/slower
alternatives operating on `RubiksCube3dArray`, mainly useful for small
scrambles or as a sanity check.

### Pattern database

The corner pattern database maps every reachable corner
permutation+orientation state to the minimum number of moves needed to
solve just the corners (ignoring edges). This gives IDA* a much better
lower-bound estimate than move-counting alone, which is what makes
double-digit-depth scrambles solvable in a reasonable time.

It's generated by a breadth-first search over all corner states
(`CornerDBMaker::bfsAndStore`), starting from the solved cube and
fanning out through all 18 possible moves at each step.

## Building

Requires a C++17 compiler and CMake 3.16+.

```bash
mkdir build && cd build
cmake ..
cmake --build .
```

This produces two executables in `build/`:

- **`RubiksCubeSolver`** — scrambles a cube to increasing depths (1–9 by
  default) and times how long IDA* takes to solve each one back,
  verifying every solution actually restores the cube.
- **`generate_corner_db`** — (re)generates `data/cornerPatternDB.bin`.
  You shouldn't need to run this — the database is already committed —
  but it's here if you want to regenerate it or experiment with a
  different search depth.

Run the solver from the **project root** (not from inside `build/`), since
it looks for the pattern database at the relative path
`data/cornerPatternDB.bin`:

```bash
./build/RubiksCubeSolver
```

If the database can't be found or doesn't match the expected file size,
the solver throws a clear error instead of silently degrading — see
[Bugs fixed](#bugs-fixed).

## Pattern database depth

Corner-only distances top out around depth 11, but a full breadth-first
search over all ~88 million corner states needs more memory than most
laptops have to spare for a queue of in-flight cube states. `CornerDBMaker`
caps the search at depth 8, which covers about 31% of all reachable corner
states — the ones a solver is most likely to actually encounter early in
a search. States deeper than that fall back to a large-but-safe sentinel
value in the heuristic, which just means IDA* explores a bit more before
proving optimality; it does not affect correctness.

If you want a stronger heuristic and have the RAM/time to spare, raise
`kMaxDepth` in `CornerDBMaker::bfsAndStore` (`src/PatternDatabases/CornerDBMaker.cpp`).

## Testing

There's no formal test suite (no GoogleTest/Catch2 dependency), but the
project was validated by:

- Cross-checking every one of the 18 moves, and every ordered pair of the
  18 moves (324 combinations), between `RubiksCubeBitboard` and the
  trusted `RubiksCube3dArray` reference.
- 20,000 randomly generated scrambles up to 100 moves long, comparing the
  two models sticker-for-sticker after every move.
- End-to-end solves at every scramble depth from 1 to 11, each verified
  by actually applying the returned move sequence and checking
  `isSolved()`.

If you want to rerun something similar, the pattern to follow is:

```cpp
RubiksCube3dArray a;
RubiksCubeBitboard b;
a.move(RubiksCube::MOVE::R);
b.move(RubiksCube::MOVE::R);
// then compare a.getColor(face, row, col) == b.getColor(face, row, col)
// for every face/row/col
```

## Bugs fixed

This codebase had one serious correctness bug and a handful of smaller
issues, all fixed:

1. **The `R` move corrupted the cube (main bug).** `RubiksCubeBitboard::r()`
   cycles 12 stickers across the UP, FRONT, DOWN, and BACK faces through
   three helper calls plus a final manual write-back into the BACK face.
   The final write used destination indices `{0, 7, 6}`; they needed to
   be `{6, 7, 0}` to match the read order used earlier in the same
   function. The mismatch silently turned what should be three
   independent 4-cycles (so that `R` applied four times returns to the
   original state, like a real cube) into a single 12-cycle. This was
   invisible on a solved cube — repeated colors masked the wrong
   cyclic order — but corrupted the cube on any sequence combining `R`
   with another face turn (e.g. `L F R2` followed by its "inverse"
   `R2 F' L'` did **not** return to solved). Found by cross-validating
   every move against a simpler, independently-implemented reference
   cube model, and confirmed fixed by 20,000 random-scramble
   cross-checks plus exhaustive pairwise move tests (all passing with
   zero mismatches after the fix). The shipped pattern database was
   regenerated from scratch afterward, since it had been built using the
   buggy move logic.

2. **Silent failure when the pattern database file was missing or the
   wrong path.** `IDAstarSolver`'s constructor called
   `cornerDB.fromFile(fileName)` without checking the return value. If
   the file wasn't found, the database silently stayed at its "unknown"
   sentinel value for every state, and the solver would just get very
   slow instead of reporting an error. It now throws a clear
   `std::runtime_error` naming the missing path.

3. **Oversized, unexplained database allocation.** `CornerPatternDatabase`
   allocated space for 100,179,840 entries with no comment explaining the
   number. The actual corner state space is exactly `8! x 3^7 =
   88,179,840`. Fixed to the exact value (documented inline), shrinking
   the database file from ~50 MB to ~44 MB.

4. **Missing copy constructors.** Both cube models defined `operator=`
   but not a copy constructor, which is a Rule-of-Three violation that
   silently falls back to the (in this case harmless, but
   compiler-flagged-deprecated) implicit copy constructor. Both now
   explicitly `= default` their copy constructor.

5. **Dead, commented-out code in `main.cpp`.** About 100 lines of an
   old, disabled validation harness were removed; the validation it did
   is now documented and reproducible (see [Testing](#testing)) instead
   of sitting inert in the shipped binary's source.

6. **No way to (re)build the pattern database.** `CornerDBMaker` existed
   but nothing in the project actually invoked it. Added
   `tools/generate_corner_db.cpp` and wired it into the CMake build as a
   second executable.

7. **Empty README, no `data/` file tracked correctly.** This file, and a
   `.gitignore` fix so the required `data/cornerPatternDB.bin` runtime
   asset isn't accidentally excluded by the blanket `*.bin` ignore rule
   that was previously in place.

## Known limitations

- The corner-only heuristic (no edge pattern database) means scrambles
  deeper than ~9-10 moves get noticeably slower to solve optimally, and
  very deep scrambles (12+) can use enough memory to be impractical on
  modest machines. A real "God's number" solver combines corner and edge
  pattern databases (as in Korf's original algorithm) for much stronger
  pruning; that's a natural next step if you want to push this further.
- `BFS`/`DFS`/`IDDFS` operate on `RubiksCube3dArray`, which is not
  optimized for speed, so they're only practical for shallow scrambles.
